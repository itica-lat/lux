Cómo está armado Lux

Lux es un sistema de gestión de equipamiento e incidencias (inventario, tickets, préstamos, solicitudes de servicio) para una institución. Este documento es solo la mitad frontend: la app React que ves corriendo con bun dev. Hay un backend real (GraphQL + MariaDB) que vive fuera de este repo — está documentado en ARQUITECTURA.md.

1 Estructura del repo

¿Por qué separar features/ de components/?
features/ son cosas que cuelgan de una ruta (montás una vez, viven en router/index.tsx). components/ no saben nada de rutas: se importan desde cualquier feature. Si movés un archivo de features/ y deja de tener sentido en el router, probablemente pertenece a components/.

3 Esquema de API

No es REST. Todo el tráfico de datos pasa por un único endpoint: POST /graphql. El "esquema" vive en src/mocks/schema.ts y las respuestas mockeadas en src/mocks/handlers.ts (interceptadas por MSW en desarrollo).

La función que envuelve todo: gql()

src/lib/utils.ts 
export async function gql<T>(query: string, variables?: Record<string, unknown>): Promise<T> {
  const response = await fetch("/graphql", {
    method: "POST",
    headers: { "Content-Type": "application/json" },
    body: JSON.stringify({ query, variables }),
  });

  if (!response.ok) {
    throw new Error(`HTTP ${response.status}: ${response.statusText}`);
  }

  const json = (await response.json()) as { data?: T; errors?: Array<{ message: string }> };

  if (json.errors && json.errors.length > 0) {
    throw new Error(json.errors[0].message);
  }
  if (!json.data) {
    throw new Error("No data returned from API");
  }
  return json.data;
}

Cada feature define sus propias queries/mutations como template strings justo arriba del componente que las usa, y las pasa a gql<T>(). No hay un cliente GraphQL (Apollo, urql) — es un fetch con tipado manual encima.

4 Base de datos y cómo se hacen requests

Este repo no tiene base de datos. Es 100% frontend. Lo que simula la base de datos en desarrollo son arrays en memoria dentro de src/mocks/data/ (mockUsers, mockProducts, mockTickets...). La base real (MariaDB) vive en el servidor de producción, documentado en ARQUITECTURA.md (sección 4).

El hook que hace los pedidos: useAsync

src/hooks/useSkeleton.ts 
export function useAsync<T>(
  fn: () => Promise<T>,
  deps: unknown[] = [],
): { data: T | null; isLoading: boolean; error: string | null; refetch: () => void } {
  const [data, setData] = useState<T | null>(null);
  const [isLoading, setIsLoading] = useState(true);
  const [error, setError] = useState<string | null>(null);
  const [trigger, setTrigger] = useState(0);

  useEffect(() => {
    let cancelled = false;
    setIsLoading(true);
    fn()
      .then((result) => { if (!cancelled) setData(result); })
      .catch((err: unknown) => {
        if (!cancelled) setError(err instanceof Error ? err.message : "Error desconocido");
      })
      .finally(() => { if (!cancelled) setIsLoading(false); });
    return () => { cancelled = true; };
  }, [trigger, ...deps]);

  const refetch = () => setTrigger((t) => t + 1);
  return { data, isLoading, error, refetch };
}

No hay React Query ni SWR. useAsync es la versión artesanal: guarda loading/error/data a mano y expone refetch. El truco del cancelled flag evita el clásico bug de "setState en un componente que ya se desmontó".

Uso real en un componente

src/features/tickets/TicketList.tsx 
const { data, isLoading, error, refetch } = useAsync<{ tickets: Ticket[] }>(
  () => gql(TICKETS_QUERY, { submittedById: isSolicitante ? user?.id : undefined }),
  [isSolicitante, user?.id],
);

¿Qué pasa si dos componentes piden la misma query al mismo tiempo?
Se disparan dos fetch independientes — no hay caché ni deduplicación (eso es justo lo que te da gratis una librería como React Query, y es el trade-off de no usarla acá).

5 Seguridad

Antes de la lista de mecanismos, la idea más importante de esta sección: en este repo la seguridad es casi toda cosmética (RBAC de UI). La aplicación real de permisos tiene que pasar por el backend — y ahí mismo se puede comprobar que, en los mocks, no pasa.

1. Los 4 roles

2. El guard de rutas: ProtectedRoute

src/components/auth/ProtectedRoute.tsx 
export function ProtectedRoute({ children, roles }: ProtectedRouteProps) {
  const { isAuthenticated, user } = useAuth();
  const location = useLocation();

  if (!isAuthenticated) {
    return <Navigate to={ROUTES.LOGIN} state={{ from: location }} replace />;
  }
  if (roles && user && !roles.includes(user.role)) {
    return <Navigate to={ROUTES.FORBIDDEN} replace />;
  }
  return <>{children}</>;
}

Se usa envolviendo rutas en router/index.tsx, por ejemplo:

{ path: "loans", element: (
  <ProtectedRoute roles={["root_admin", "admin", "tecnico"]}>
    <LoansPage />
  </ProtectedRoute>
) }
Actualizado — este gap ya se corrigió
Antes, gql() nunca mandaba el token en un header, y las mutations del mock no verificaban el rol de quien llamaba. Ahora:
  • gql() (src/lib/utils.ts) lee el token de localStorage y lo manda como Authorization: Bearer <token> en cada request.
  • src/mocks/handlers.ts resuelve al usuario que llama desde ese header (getCaller(request), simulando la verificación de un token real) en vez de leer localStorage directamente dentro del handler.
  • Cada mutation que cambia estado sensible verifica el rol del caller con hasRole(caller, ALLOWED_ROLES) antes de ejecutar nada — si llamás gql(CREATE_LOAN_MUTATION, ...) desde la consola sin un token válido de un rol permitido, el mock devuelve un error en vez de ejecutar la mutation.
// src/mocks/handlers.ts
function getCaller(request: Request): User | null {
  const token = request.headers.get("Authorization")?.match(/^Bearer (.+)$/)?.[1];
  const userId = token?.match(/^mock-token-(.+)$/)?.[1];
  return userId ? (mockUsers.find((u) => u.id === userId && u.isActive) ?? null) : null;
}

function hasRole(caller: User | null, allowedRoles: UserRole[]): caller is User {
  return caller !== null && allowedRoles.includes(caller.role);
}

graphql.mutation("ApproveLoan", ({ request, variables }) => {
  if (!hasRole(getCaller(request), ELEVATED_ROLES)) {
    return HttpResponse.json({ errors: [{ message: "No tenés permisos para esta acción" }] });
  }
  // ...
});

ProtectedRoute sigue escondiendo botones por UX, pero ahora hay una segunda barrera real detrás. Sigue siendo un mock: el backend de producción real es el que tiene que hacer esta misma verificación contra la base de datos, no contra un array en memoria.

3. La matriz de permisos (documentación, no enforcement)

src/features/admin/RolesConfig.tsx

Define 15 permisos (view_dashboard, edit_inventory, assign_tickets, manage_users...) mapeados a roles, y los muestra en una tabla dentro del panel de admin. Sigue siendo solo una vista de referencia para humanos — el enforcement nuevo en handlers.ts usa dos grupos de roles más simples (STAFF_ROLES / ELEVATED_ROLES) derivados de cómo la UI ya usaba hasRole() en cada feature, no este array de 15 permisos.

4. Dónde vive la sesión

src/hooks/useAuth.ts 
const STORAGE_KEY = "lux_auth";
// ...
localStorage.setItem(STORAGE_KEY, JSON.stringify(authUser)); // authUser incluye el token

localStorage no es httpOnly: cualquier script que logre correr en la página (XSS) puede leer el token. La defensa contra XSS que sí existe es implícita: React escapa por defecto todo lo que renderiza en JSX.

5. Dónde está la seguridad "de verdad"

Firewall (UFW), TLS/Nginx, hardening del sistema operativo y la base de datos: todo eso vive en el servidor de producción, fuera de este repo — ver ARQUITECTURA.md, sección 4 ("Instalación del servidor").

Ya se agregó el header y el chequeo de rol en el mock. ¿Qué falta para que esto sea seguridad real y no solo una simulación más completa?
Que el backend de producción (fuera de este repo) haga exactamente esta misma verificación: leer el token, resolver el usuario contra la base de datos real (no un array en memoria) y rechazar la mutation si el rol no alcanza. El mock ahora demuestra el patrón correcto, pero un mock nunca es la barrera real — solo evita que te acostumbres a que no exista ninguna.

6 TypeScript: cómo está aplicado

tsconfig.app.json tiene "strict": true, más algunas opciones menos comunes que vale la pena entender porque explican patrones que vas a ver en todo el código.

OpciónQué obliga
strict: trueNo any implícito, null-checks estrictos, etc.
verbatimModuleSyntax: trueLos imports que son solo tipos tienen que escribirse import type, si no, error de compilación
erasableSyntaxOnly: trueProhíbe sintaxis de TS que genera código en runtime (enums con valores, namespaces, parameter properties) — todo tiene que poder "borrarse" al compilar a JS
noUnusedLocals / noUnusedParametersVariable o parámetro sin usar = error, no warning

Consecuencia directa de erasableSyntaxOnly: como no se permiten los enum de TS (generan un objeto en runtime), el repo usa uniones de literales de string en su lugar:

export type TicketStatus = "pending" | "in_progress" | "in_resolution" | "resolved";
export type EquipmentStatus = "available" | "in_use" | "in_repair" | "retired";

Uniones discriminadas

src/lib/types.ts

Product y Component comparten un campo type que actúa de discriminante, permitiendo un tipo combinado:

export interface Product { id: string; type: "product"; /* ... */ }
export interface Component { id: string; type: "component"; /* ... */ }
export type Equipment = Product | Component;

Con esto, if (equipment.type === "product") hace que TypeScript "estreche" (narrow) el tipo dentro del if sin necesidad de castear nada.

Genéricos en las dos piezas centrales

function gql<T>(query: string, variables?: Record<string, unknown>): Promise<T>
function useAsync<T>(fn: () => Promise<T>, deps: unknown[]): { data: T | null; ... }

// uso: el tipo de retorno se infiere en el call site
useAsync<{ tickets: Ticket[] }>(() => gql(TICKETS_QUERY, vars), [deps]);
Un patrón declarado pero no adoptado
src/lib/types.ts:147 define type Result<T, E = Error> = { ok: true; value: T } | { ok: false; error: E } — el típico "Result type" para manejar errores como valores en vez de try/catch. Pero no se usa en ningún otro archivo del repo: todo el manejo de errores real pasa por throw + .catch() (ver useAsync, sección 4). Es un tipo aspiracional, no una convención vigente — si lo adoptás, hacelo consistente en todo el flujo de datos, no en un solo componente.
¿Por qué no hay ningún enum en types.ts?
erasableSyntaxOnly en tsconfig.app.json lo prohíbe directamente (no compila). Las uniones de string literales cumplen el mismo rol y desaparecen por completo al transpilar — no dejan rastro en el JS final.

Lo que no hay, a propósito
Sin cliente GraphQL (Apollo/urql), sin librería de formularios, sin manejo de estado global (Redux/Zustand), sin datepicker. Todo eso está resuelto con fetch + useState + Context — menos dependencias, más código explícito a la vista.
¿Por qué tailwind-merge además de clsx?
clsx solo concatena clases condicionalmente; no sabe que p-2 y p-4 son la misma propiedad CSS. Si un componente base tiene p-2 y el caller pasa p-4 para sobreescribir, clsx deja las dos y gana la que venga después en el CSS final (frágil). twMerge entiende Tailwind y descarta la que corresponde.
